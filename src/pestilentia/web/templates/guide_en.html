Overview

Elementary CTI is a Cyber Threat Intelligence platform that specializes in monitoring ransomware threats. It aggregates data from multiple sources into a unified database, enriches it with tactical, financial, and operational information, and presents it through an interactive web interface.

Data sources

The platform integrates the following intelligence sources:

  • ransomware.live — Primary feed: ransomware groups, victims, cyberattacks, dark web infrastructure, BTC addresses, file extensions, group lineage
  • MITRE ATT&CK — Tactical enrichment: techniques (TTPs), software tools, aliases, references, mapping by tactic (Initial Access, Execution, Persistence, and more)
  • Ransomwhere — Financial enrichment: BTC payments associated with ransomware families, with USD amounts and transaction dates
  • deepdarkCTI — Operational enrichment: onion site status (online/offline), communication channels (Tox, Telegram, Twitter, email, Jabber), RSS feeds

Navigation

Use the sidebar on the left to access the different sections. The global search box at the top right lets you quickly search victims, groups, and attacks from any page. The alert counter in the sidebar shows unread watchlist notifications.

Data updates

The scheduler updates data automatically every 2 hours for the primary feeds and weekly for the enrichment sources. You can force a manual update from the Pipeline page or through the POST /api/v1/refresh API.

Dashboard

The dashboard is the platform's landing page and gives an overview of the ransomware threat landscape.

Summary cards

The top section shows the main counters: total victims, adversary groups, recorded cyberattacks, countries involved, and active data sources. The source counter includes both the primary data feeds (for example, ransomware.live) and the active enrichment sources (MITRE, Ransomwhere, deepdarkCTI).

Recent victims

The recent victims table shows the latest recorded victims with name, responsible group, country, and date. Three tabs filter by period: last 7 days, last month, last year. Click any row to open the victim detail page.

Geographic map

The choropleth map shows the global distribution of victims. Colors range from light yellow (few victims) to dark red (many victims), using a quantile scale to highlight differences between countries. Hover over a country to see the exact count.

Most active groups

The bottom section shows the ransomware groups with the highest number of victims, with pixel-art avatars generated deterministically from the group name and a short description.

Victims

Complete list of all ransomware victims recorded in the platform, with paginated navigation (50 items per page).

Filters

  • Free text — Search by victim name or web domain. The search is case-insensitive and supports partial matches.
  • Group — Drop-down menu to filter victims of a specific group (for example, lockbit, akira, clop).
  • Country — Drop-down menu to filter by the ISO code of the victim's country (for example, US, IT, DE).

You can combine filters. For example, you can search for all Italian victims of the LockBit group that contain "bank" in the name.

Victim detail

Click a victim to open the detail page, which shows: name, domain, country, attack date, responsible group, related organizations, and any cross-source duplicates (the same victim reported by different sources). Duplicates are identified through fuzzy matching on the name and domain.

Adversaries

Catalog of the ransomware groups monitored by the platform. Each group is identified by a deterministically generated pixel-art avatar, a victim count, and a short description. Hacktivist groups are marked with an orange badge and their "victims" are labeled as "claims" to reflect the different nature of their activities.

Group detail page

The detail page of each group is organized into six tabs, preceded by a choropleth map that shows the geographic distribution of victims. If the group's country of origin is known, it is highlighted with blue diagonal bands on the map.

  • Overview — Complete group profile: description, country of origin, operation type (for example, RaaS, Locker, Data Broker), lineage (relationships with other groups), file extensions used for encryption, known aliases. Includes the Diamond Model (adversary-victim-infrastructure-capability relationship) and Pyramid of Pain (indicators from hashes to TTPs) analytic models.
  • Infrastructure — Dark web sites (.onion URLs) with operational status (online/offline). Financial Intelligence section with aggregated BTC payment statistics: total USD received, total BTC, transaction count, wallet address count. BTC addresses are clickable and linked to blockchain.com for verification. Communication Channels section with the group's operational channels (Tox ID, Telegram handle, Twitter account, email, Jabber).
  • Arsenal — Software tools used by the group, categorized by function: credential theft (Mimikatz, LaZagne), defense evasion, command and control (Cobalt Strike, Brute Ratel), lateral movement, data exfiltration. Data comes from the MITRE ATT&CK enrichment.
  • TTPs — MITRE ATT&CK techniques associated with the group, organized by tactic (Initial Access, Execution, Persistence, Privilege Escalation, Defense Evasion, Credential Access, Discovery, Lateral Movement, Collection, Command and Control, Exfiltration, Impact). Each technique is identified by its MITRE code (for example, T1566) and name.
  • Victims — List of the group's recent victims with name, country, and attack date. For hacktivist groups, the column is named "Title" instead of "Name" and the domain is hidden, because the entries are often article titles rather than organization names.
  • References — Badges of the data sources that contribute to the group profile, CISA (Cybersecurity and Infrastructure Security Agency) alerts, published threat reports, direct links to the group's MITRE ATT&CK page.

Cyberattacks

Paginated list of all cyberattacks recorded in the platform. Cyberattacks represent specific attack events, distinct from victims: the same victim can be associated with multiple attacks over time, and an attack can carry additional information such as announcement titles, publication dates, and descriptions.

Available filters

  • Free text — Search by victim name or attack announcement title.
  • Country — Filter by the ISO country code of the affected victim.

Results show: victim name, country, attack date, announcement title. Each row links to the corresponding victim detail page.

Map

Full-screen interactive choropleth map that shows the global distribution of ransomware victims by country.

Time filter

Five filter options let you analyze threat activity over different periods:

  • 7 days — Current week's activity, useful for daily operational monitoring.
  • 15 days — Two-week view, useful for spotting short-term trends.
  • 1 month — Monthly overview for periodic reports.
  • 1 year — Annual distribution for medium-term trend analysis.
  • All — Complete historical data since the first collection (default).

Interaction

Hover over a country to see the exact victim count in a tooltip. The color scale uses the YlOrRd (yellow-orange-red) palette with quantile binning to maximize readability even with highly skewed distributions (for example, the US with thousands of victims versus countries with single digits). Click a country to filter the victim list.

BTC Explorer

Search and analysis tool for Bitcoin addresses associated with ransomware groups. Data comes from the Ransomwhere enrichment, which tracks victim payments to group-controlled wallets.

Summary cards

The top of the page shows aggregated statistics: total USD received by all groups, total BTC, number of tracked transactions, and number of distinct wallet addresses.

Address search

The search box lets you search BTC addresses by partial match. Enter the beginning of an address (for example, bc1q...) to find all matching wallets. Results show: address, associated group, transaction count, total BTC, total USD, first and last transaction date.

Top 20

Without an active search, the page shows the 20 addresses with the highest received BTC volume, useful for identifying the most relevant wallets in the ransomware ecosystem. Each address links to blockchain.com for on-chain verification.

Search

Global search engine that queries all platform entities at once: victims, adversary groups, and cyberattacks.

How it works

Enter one or more keywords in the search box. The search is case-insensitive and looks for partial matches in the following fields:

  • Victims — Victim name, web domain
  • Groups — Group name, known aliases, description
  • Cyberattacks — Victim name, announcement title

Results are grouped by category and capped at 20 items per type. The search is also available from the box at the top right of the navigation bar, on every page.

Watchlist

Proactive monitoring system for specific companies and organizations. It sends immediate notifications when a new victim matches a watchlist target.

Add a target

Fill in the form with the name of the company to monitor and, optionally, the web domain and additional keywords. Matching uses a fuzzy algorithm (configurable threshold, default 85%) that compares the victim name with the watchlist targets, tolerating capitalization changes, abbreviations, and small typos.

Alerts and notifications

When a data refresh identifies a new victim that matches a watchlist target, the platform generates an alert visible on the Watchlist page and updates the counter in the sidebar. You can mark alerts as read one by one or all at once. Notifications are also sent to the configured channels:

  • Log — Default channel, writes alerts to the application log.
  • Webhook — Sends an HTTP POST request with a JSON payload to a configured URL. Supports retry with exponential backoff and authentication through a secret header.

Management

You can delete watchlist targets with the delete button. Deletion removes the target from monitoring but keeps the alerts already generated.

Pipeline

Control panel for monitoring and managing the data collection and enrichment pipeline.

Source cards

Each data and enrichment source has a card with its current state (Active, Backfilling, Disabled, Not run) and a switch to enable or disable it. Disabled sources are skipped both by the automatic scheduler and by manual refreshes. A colored indicator (green/yellow/red) shows the result of the last health check.

Backfill Progress

Table that shows the historical backfill status for each primary data source. The backfill retrieves historical data year by year, from the platform's start date (2020) to the current year. Once complete, the source switches to incremental mode (new data only).

Enrichment Sources

Table of enrichment sources with: health check status (ok/degraded/down), last enrichment date, type of data provided, and key metrics (for example, TTP count for MITRE, transaction count for Ransomwhere, channel count for deepdarkCTI).

Source Health

Section dedicated to monitoring the health of external sources. For each source, the platform checks: HTTP reachability, validity of the received data format, and the number of rows/records (for deepdarkCTI). A summary banner at the top indicates whether all sources are operational or there are problems. The "Run Check" button runs all checks immediately. The scheduler also runs the checks automatically after each enrichment cycle.

Data Sources

Table with statistics for each primary data source: base URL, number of imported victims, groups, and attacks. Useful for verifying how data is distributed across sources.

Data Pipeline

Elementary CTI collects data from multiple threat intelligence sources on a schedule. The pipeline runs automatically and can be monitored from the Pipeline page.

Data Sources

Source Type Frequency Data
ransomware.liveREST APIEvery 2 hoursGroups, victims, cyberattacks, dark web infrastructure, BTC addresses, file extensions, group lineage, profile links
MITRE ATT&CKSTIX 2.1 Bundle (JSON)WeeklyTTPs by tactic, software tools by category, group aliases, references (reports, CISA alerts). Matching by normalized name and aliases
RansomwhereREST API (JSON)WeeklyBTC transactions associated with ransomware families: wallet address, transaction hash, BTC amount, USD value, date. Primary matching by BTC address, secondary by family name
deepdarkCTIMarkdown (GitHub)WeeklyThree files: (1) ransomware_gang.md — onion site status, URLs, credentials, RSS feeds; (2) telegram_threat_actors.md — operational Telegram channels; (3) twitter_threat_actors.md — Twitter/X accounts. Matching by normalized name

Data Collection Flow

The pipeline operates in two phases: initial backfill (historical data) and incremental update (new data only).

Phase 1: Backfill

  1. Retrieve historical data year by year (from 2020 to the current year)
  2. Create groups, victims, and cyberattacks in the database
  3. Completion is recorded in info_updates — the source automatically switches to the incremental phase

Phase 2: Incremental Update

  1. Retrieve recent victims and new cyberattacks from ransomware.live
  2. Match the watchlist with the fuzzy algorithm — generate alerts for new matches
  3. Dispatch notifications to the configured channels (log, webhook)

Phase 3: Enrichment (post-cycle)

  1. MITRE ATT&CK — Download the STIX bundle, verify freshness (hash), match groups by name/alias, import TTPs and tools
  2. Ransomwhere — Download the full export, match families by BTC address and name, import transactions with deduplication
  3. deepdarkCTI — Download and parse the 3 markdown files, match gangs by name, import onion URLs and communication channels (Tox, Telegram, Twitter, email)
  4. Health Check — Verify reachability and integrity of all external sources

The raw JSON from each source is saved in group_source_data for future cross-source verification and historical reconstruction.

Controls

Each data and enrichment source (ransomware.live, MITRE ATT&CK, Ransomwhere, deepdarkCTI) can be enabled or disabled individually from the Pipeline page through toggle switches. Disabled sources are skipped both by the automatic scheduler and by manual refreshes through the API. The state is persisted in the database and survives application restarts.

Health Monitoring

The monitoring system periodically checks the health of external sources. For each source, it checks:

  • Reachability — Verifies that the HTTP endpoint responds with status 200
  • Format validity — For deepdarkCTI: parses the markdown tables and verifies that the row count is above the minimum threshold (for example, 400 for ransomware_gang, 500 for telegram_threat_actors)
  • Status — ok (reachable and valid), degraded (reachable but anomalous format), down (unreachable)

The checks run automatically after each enrichment cycle in the scheduler. You can also run them manually with the "Run Check" button on the Pipeline page or through POST /api/v1/health.

Threat Intelligence Glossary

Definitions oriented toward operational relevance, not just academic accuracy. Sources: MITRE ATT&CK, SANS, NICCS/CISA, Team Cymru.

{# ── Ransomware & Threat Actors ── #}

Ransomware & Threat Actors

Ransomware

Malware that encrypts the victim's data and demands a ransom for the decryption key. Modern operations use "double extortion" (encryption + data exfiltration). Infrastructure is often reused across nominally distinct groups through Ransomware-as-a-Service (RaaS) models.

RaaS (Ransomware-as-a-Service)

Operating model in which ransomware developers provide the malware and infrastructure to affiliates, who carry out the attacks in exchange for a share of the ransom (typically 20-30% to the developers). It explains the proliferation of groups with similar infrastructure.

APT (Advanced Persistent Threat)

Actor — typically nation-state — characterized by high capability, long dwell time, and mission-focused objectives (espionage, IP theft). It differs from ransomware in motivation (non-financial) and in its investment in OPSEC and long-term persistence.

Hacktivist

Ideologically motivated actor that carries out attacks (DDoS, defacement, data leaks) for political or social reasons. In Elementary CTI, hacktivist groups are flagged automatically and their "victims" are labeled as "claims" to reflect the different nature of their activities.

Lineage

Genealogical relationships between ransomware groups: forks, rebrands, affiliations. For example, BlackMatter → ALPHV/BlackCat → possible link to DarkSide. Lineage helps predict the TTPs and infrastructure of new groups based on their predecessors.

Double Extortion

Technique in which the attacker first exfiltrates the data, then encrypts the systems. If the victim does not pay, the data is published on the group's leak site. Now standard for most modern ransomware operations.

{# ── Threat Intelligence Concepts ── #}

Threat Intelligence Concepts

CTI (Cyber Threat Intelligence)

Analyzed and contextualized information about adversaries, capabilities, and intentions, produced to support decisions. Good CTI answers "who, what, why, and how?" — not just "which IP?". The intelligence cycle — collection, processing, analysis, dissemination, feedback — applies to CTI as it does to any other intelligence discipline.

IOC (Indicator of Compromise)

Observable artifact — IP address, domain, hash, registry key, certificate SHA-256 — that indicates a compromise. IOCs are short-lived: actors change them as soon as they are published. In Elementary CTI, the main IOCs are the groups' BTC addresses and .onion sites.

TTP (Tactics, Techniques & Procedures)

The "how" of an attack — the methods and patterns used to achieve objectives. TTPs are the most durable intelligence: indicators rotate in days, infrastructure in weeks, but TTPs stay stable for months or years. MITRE ATT&CK is the standard taxonomy. Elementary CTI maps TTPs for each group in the dedicated tab.

Diamond Model

Analytic framework that models an intrusion event as a relationship between four vertices: Adversary, Capability, Infrastructure, Victim. Each pair of vertices defines an analysis axis (for example, Adversary-Infrastructure for pivoting). In Elementary CTI, the Diamond Model is shown in the Overview tab of each group.

Pyramid of Pain

David Bianco's model that ranks indicators by the "pain" they cause the adversary when detected: from the base (hashes — easy to change) to the top (TTPs — hard to change). In Elementary CTI, the Pyramid of Pain shows which indicator levels are available for each group.

MITRE ATT&CK

Knowledge base of adversary tactics and techniques based on real-world observations. Organized into 14 tactics (from Reconnaissance to Impact), with hundreds of specific techniques. Elementary CTI uses the STIX bundle to enrich group profiles with documented TTPs and software tools.

Attribution

Process of identifying the actor behind an intrusion. Full attribution (individual or state unit) is difficult and rarely necessary for defense. Tactical attribution — identifying an actor cluster through infrastructure overlap, TTP patterns, and malware similarity — is operationally useful and achievable.

Victimology

Study of who gets hit, why, and in what sequence. Victimology helps profile the actor's motivation (espionage, financial, hacktivism), predict future targets, and validate attribution hypotheses. Elementary CTI visualizes the geographic distribution of victims to identify targeting patterns.

{# ── Infrastructure & Financial ── #}

Infrastructure & Financial Intelligence

Leak Site / DLS (Data Leak Site)

Dark web (.onion) site where the ransomware group publishes data exfiltrated from victims who do not pay the ransom. The operational status (online/offline) of leak sites is tracked by deepdarkCTI and is an indicator of the group's current activity.

BTC Address (Wallet)

Bitcoin address used by the group to receive ransom payments. Traceable on the public blockchain. In Elementary CTI, Ransomwhere data maps addresses → families → transactions with USD amounts. Useful for estimating a group's revenue and identifying financial relationships.

C2 (Command & Control)

Command infrastructure used to control compromised systems: remote servers, encrypted channels, DGA. In the ransomware context, the C2 coordinates the exfiltration phase and the deployment of the encryption payload. The communication channels (Tox, Telegram) tracked by deepdarkCTI are used for ransom negotiation.

Tox ID

Identifier in the Tox messaging protocol (peer-to-peer, encrypted). Frequently used by ransomware groups to communicate with victims during ransom negotiation, because it requires no registration and cannot be censored.

STIX (Structured Threat Information eXpression)

OASIS standard for representing threat intelligence in structured JSON format. MITRE ATT&CK distributes its database as a STIX 2.1 bundle. Elementary CTI downloads and processes this bundle to extract TTPs, tools, and relationships between groups.

OSINT (Open Source Intelligence)

Intelligence derived from publicly accessible sources. deepdarkCTI is an OSINT project that curates information about ransomware groups from open sources (GitHub repositories, forums, Telegram/Twitter channels). It complements the structured API sources with community-updated operational data.

{# ── Defensive & Analysis ── #}

Defense & Analysis

Threat Hunting

Proactive, hypothesis-driven process of searching for adversary activity that bypassed automated detection. A hunt starts with a hypothesis (for example, "is there Cobalt Strike C2 traffic from the internal network?"), collects relevant data, analyzes it, and confirms or refutes the hypothesis.

Incident Response

Structured process to detect, contain, eradicate, and recover from a security incident. The intelligence function supports IR by characterizing the actor, scoping the infrastructure, and identifying persistence mechanisms.

Fuzzy Matching

Approximate string comparison algorithm that tolerates capitalization changes, abbreviations, and small errors. In Elementary CTI, it is used for: (1) watchlist matching (85% threshold), (2) correlating group names across sources, (3) identifying cross-source duplicates.

Enrichment

Process of adding context and intelligence to raw data from external sources. In Elementary CTI, enrichment operates on three axes: tactical (MITRE ATT&CK → TTPs), financial (Ransomwhere → BTC payments), operational (deepdarkCTI → infrastructure status, communication channels).

{# ── ransomware.live ── #}

ransomware.live

Active REST API Every 2 hours

Endpoint

/api/groupsGroup list with basic metadata
/api/victims/{year}Victims by year (historical backfill)
/api/recentvictimsRecent victims (incremental update)
/api/cyberattacksCyberattack feed with titles and dates
/v2/group/{name}Group detail: type, extensions, lineage, BTC, profiles

Imported fields

  • group_name, description, country_of_origin — basic profile
  • group_type (RaaS, Locker, Data Broker, and more), extensions (encrypted file extensions)
  • lineage — relationships with other groups (predecessors, forks, rebrands)
  • btc_addresses — known BTC wallet addresses (used as the primary key for Ransomwhere matching)
  • profile_urls — links to .onion sites and clearnet mirrors
  • altname — additional aliases (merged with MITRE aliases)
  • victim_name, domain, country, attackdate — victim record

Operational flow

  1. Initial backfill: retrieve year by year (2020→today), create groups + victims + attacks
  2. Incremental: only /api/recentvictims → new records deduplicated by (name, group, date)
  3. Detail enrichment: /v2/group/{name} → type, extensions, lineage, BTC, profiles
  4. Raw JSON saved in group_source_data for the audit trail

Limitations

  • → No authentication required, but rate limiting is undocumented — kept at 1 req/s
  • → Country attribution data is not always available (many groups lack country_of_origin)
  • → Duplicate victims are possible: the same organization with slightly different names in different periods
  • → The /v2/group endpoint can return null fields for less-documented groups
{# ── MITRE ATT&CK ── #}

MITRE ATT&CK

Active STIX 2.1 Bundle Weekly

Data source

JSON bundle (~30 MB) from github.com/mitre-attack/attack-stix-data/master/enterprise-attack/enterprise-attack.json

Processed STIX objects

intrusion-setAdversary groups → matched with Group by name/alias
attack-patternATT&CK techniques → GroupTTP table (technique_id, name, tactic)
tool / malwareSoftware tools → GroupTool table (name, type, description)
relationshipLinks groups ↔ techniques ↔ tools via source_ref/target_ref

Matching logic

  1. Compute the SHA-256 hash of the bundle → compare with the previous hash (skip if identical)
  2. Extract intrusion-sets with names and aliases (x_mitre_aliases)
  3. Normalize the name: lowercase, remove spaces/hyphens
  4. Match: normalized name == normalized Group.group_name, or present in Group.aliases
  5. For each matched group: import TTPs and tools linked via relationship
  6. Merge MITRE aliases with existing aliases (case-insensitive deduplication)

Limitations

  • → Only ~42 ransomware groups have MITRE entries (out of ~360 monitored)
  • → Heavy bundle (~30 MB): full download on each check, mitigated by the freshness hash
  • → MITRE updates the bundle a few times per month — data is not real-time
  • → MITRE names use different capitalization/spacing than ransomware.live (for example, "FIN7" vs "fin7"): normalization is required
  • → Some MITRE groups are APTs, not ransomware — they match only if also present in ransomware.live

Ransomwhere

Active REST API (JSON) Weekly

Endpoint

GET https://api.ransomwhe.re/export — Full export of all known BTC transactions

Response format

{ "result": [
  { "address": "bc1q...", "family": "REvil", "transactions": [
    { "hash": "abc123...", "amount": 150000000, "amountUSD": 42000, "time": 1625097600 }
  ]}
]}
  • address — BTC address of the group's wallet
  • family — Ransomware family name (to be mapped to Group)
  • amount — Amount in satoshi (÷ 10⁸ for BTC)
  • amountUSD — USD value at transaction time
  • time — Unix timestamp of the transaction
  • hash — Transaction hash (verifiable on a blockchain explorer)

Matching logic (dual strategy)

  1. Primary — BTC address: Builds an address→Group index from Group.btc_addresses (JSON). If the Ransomwhere address is already known for a group, direct match (highest confidence).
  2. Secondary — Family name: Normalizes the family field and compares it with group names/aliases. Skip list for ambiguous names ("unknown", "generic", and so on).
  3. For each match: insert GroupBtcTransaction with deduplication on (address, tx_hash).
  4. Update Group.btc_addresses with newly discovered addresses.

Investigation Playbook

Operational guide for the analyst: how to use Elementary CTI to investigate ransomware threats, correlate indicators, and produce actionable intelligence.

{# ── Quick Triage ── #}
01

Quick Triage — Reported victim

Scenario: an organization in your watchlist has been reported as a victim. Quick triage steps:

  1. Verify the alert — Go to Watchlist. Verify the match. Check the fuzzy matching confidence score: above 95% = almost certain, 85-95% = manually verify the name/domain.
  2. Identify the group — Click the victim to see the responsible group. Open the group profile.
  3. Assess the threat — Overview tab: is it a known group? Does it have documented TTPs? Is it RaaS (more organized) or a single operator? Check the lineage to understand its history.
  4. Check the infrastructure — Infrastructure tab: is the leak site online? Are there active communication channels? If the site is online and the victim is listed, the situation is confirmed.
  5. Financial intelligence — Financial Intelligence: how much has this group collected? Groups with high BTC volume = established operations, lower chance of a favorable negotiation.
  6. Victim history — Victims tab: how many recent victims? A very active group indicates ongoing operational capability. Check for victims in the same sector/country.
{# ── Pivot Strategies ── #}
02

Pivot Strategies — Expand the investigation

Given a group or a victim, these pivot strategies let you expand the analysis. Ordered by signal quality (from most reliable to weakest):

1

BTC Clustering

Search the group's BTC addresses in the BTC Explorer. Addresses used by the same wallet cluster can reveal other linked groups or rebrands. Quality: high — cryptographic on-chain evidence.

2

Lineage & Rebrand

Check the "Lineage" field in the Overview tab. A group with known predecessors often inherits TTPs, infrastructure, and target sector preferences. Search the predecessors to compare the profiles. Quality: high — documented relationships.

3

TTP Overlap

In the TTPs tab, identify the key techniques (Initial Access, Execution). Search for other groups with the same technique set — it indicates shared tooling or a common RaaS affiliation. Quality: moderate — TTPs can be common across independent groups.

4

Arsenal Overlap

Compare the tools in the Arsenal tab. Groups that use the same specific combination (for example, Cobalt Strike + Mimikatz + Rclone) can share affiliates or operating manuals. Quality: moderate — tools are common across the ecosystem.

5

Targeting Pattern

Analyze the geographic distribution of victims on the map. Groups with similar patterns (for example, excluding CIS countries, focusing on a specific sector) can have common motivations or mandates. Use the time filters to identify campaigns. Quality: moderate — indirect correlation.

6

Communication Channel Overlap

Check the channels in the Infrastructure tab. Groups that share the same Telegram channel or use the same Tox ID in different periods can be rebrands. Quality: low — channels can be reused or shared for negotiation.

{# ── Confidence Assessment ── #}
03

Confidence Framework — Assess the profile

The confidence of a group profile depends on the number and quality of converging sources. Use this scale to assess how complete and reliable a profile is:

LevelConverging sourcesOperational meaning
High 4/4 sources (ransomware.live + MITRE + Ransomwhere + deepdarkCTI) Complete profile. TTPs, financial data, and operational status available. Can support immediate response decisions and stakeholder reporting.
Medium 2-3 sources (for example, ransomware.live + deepdarkCTI, or + MITRE) Partial profile. Enough information for triage and first response. Financial or tactical gaps require additional research for critical decisions.
Low 1 source (ransomware.live only) Basic data only (name, victims, description). No TTPs, no financial data, no operational channels. Useful for awareness, insufficient for operational decisions.
{# ── Reporting ── #}
04

Produce Intelligence — From observation to report

When you produce a report or briefing based on Elementary CTI data, follow this structure:

Executive Summary

1-2 sentences: who attacked, who was hit, when, estimated impact. Example: "The Akira group claimed company X on April 15. Akira is a RaaS operator active since 2023 with 438 known victims and $12M in tracked BTC payments."

Threat Assessment

Group profile: type, origin, lineage, main TTPs (from the MITRE tab), known tools (from Arsenal). Confidence level based on the available sources.

Indicators

BTC addresses (from Financial Intelligence), leak site URLs (from Infrastructure), communication channels (from deepdarkCTI). Label each indicator with its source: [ransomwhere], [deepdarkcti], [ransomware.live].

Context & Pattern

Victim distribution map, temporal trends (7d/1m/1y filter), comparison with other groups in the same family/lineage. Highlight whether the targeting is consistent with the group's known patterns.

Gaps & Next Steps

What we do not know: missing data, unmatched sources, low confidence on specific aspects. Recommended actions: watchlist monitoring, additional OSINT research, IOC sharing with the community.

{# ── Common Workflows ── #}
05

Common workflows

"A new group has appeared — who are they?"

  1. Search the name in Search → check whether it already exists under a different name (alias)
  2. If new: wait for the next refresh to get complete data from ransomware.live
  3. Check deepdarkCTI: does it already have a leak site? Telegram channels?
  4. Check MITRE: are there documented TTPs? (probably not for brand-new groups)
  5. Check the lineage: is it a rebrand? Look for similarities in name, infrastructure, victims

"What is the threat trend this month?"

  1. Dashboard → "1 month" tab for recent victims
  2. Map → "1 month" filter for the current geographic distribution
  3. Dashboard → "Most active groups" section to see who is hitting hardest
  4. Pipeline → Enrichment Sources to verify that the data is up to date
  5. Compare with the "1 year" filter to identify anomalies vs the baseline

"A customer wants to know the risk for their sector/country"

  1. Victims → filter by the customer's country
  2. Identify the most active groups against that country (group tab → map)
  3. For each relevant group: profile TTPs, initial access vectors, tools
  4. BTC Explorer: estimate the financial volume of the active groups (indicates organization)
  5. Produce a briefing with: top groups, most used TTPs, relevant IOCs, defensive recommendations based on TTPs

Frequently Asked Questions

What is Elementary CTI?

A Cyber Threat Intelligence platform that specializes in monitoring ransomware threats. It aggregates data from multiple sources (ransomware.live, MITRE ATT&CK, Ransomwhere, deepdarkCTI), enriches it with tactical, financial, and operational information, and presents it through an interactive web interface.

Where does the data come from?

Four main sources: (1) ransomware.live — API with groups, victims, attacks, infrastructure; (2) MITRE ATT&CK — STIX bundle with TTPs and tools; (3) Ransomwhere — JSON export with BTC transactions; (4) deepdarkCTI — markdown files with onion site status and communication channels. The scheduler updates the data automatically.

How often is the data updated?

The primary feed (ransomware.live) is updated every 2 hours. The enrichment sources (MITRE, Ransomwhere, deepdarkCTI) weekly (168 hours). All intervals are configurable through environment variables. You can force a manual update from the Pipeline page or through the API.

How does the watchlist work?

Add the name of a company (and optionally a domain and keywords). On each refresh, the system compares new victims with the targets using fuzzy matching (85% threshold). When it finds a match, it generates an alert and sends notifications to the configured channels (log, webhook). Matching is case-insensitive and tolerates abbreviations and small variations.

What does it mean when a group is "hacktivist"?

Some groups (for example, Handala, Anonymous Sudan) are not traditional ransomware but ideologically motivated actors. The system identifies them automatically from the description and adapts the interface: "victims" become "claims", titles replace organization names, and an orange badge indicates the group's hacktivist nature.

How does matching across different sources work?

Matching operates on multiple levels: (1) by BTC address when available (Ransomwhere → Group.btc_addresses); (2) by normalized name (lowercase, spaces/hyphens removed); (3) by known aliases (MITRE aliases + ransomware.live altname). Ambiguous or generic names are excluded to avoid false positives.

What does the "degraded" status in the health check mean?

The source is reachable (HTTP 200) but the data format is anomalous — typically the number of parsed rows is below the expected minimum threshold. It can mean that the source file was truncated, changed format, or that the source is having temporary problems. The system keeps working with the data already available.

Can I disable individual sources?

Yes. On the Pipeline page, each source has a toggle switch. Disabled sources are skipped both by the automatic scheduler and by manual refreshes through the API. The state is persisted in the database and survives restarts. Useful for debugging, reducing load, or isolating problems.

How do I interpret the BTC data?

The Financial Intelligence section shows the BTC transactions associated with the group: total USD received, total BTC, transaction count, and distinct wallet addresses. The data comes from Ransomwhere and represents victim payments tracked on the public blockchain. Addresses link to blockchain.com for on-chain verification. The USD value uses the rate at transaction time.

Does the platform require authentication?

Not in the current version — it is designed for internal use or on a private network. All endpoints (web and API) are accessible without credentials. For production deployments, place a reverse proxy with authentication in front of the application.

Assessment Methodology

How Elementary CTI collects, enriches, and presents ransomware threat data.

Core principles

  • 1.Multi-source convergence — No single source is reliable in isolation. Confidence increases when independent sources converge on the same signal. A group that appears in ransomware.live, has documented TTPs in MITRE, BTC transactions in Ransomwhere, and onion sites in deepdarkCTI has a high-confidence profile.
  • 2.Freshness tracking — Every data point has a collection timestamp. Intelligence has an expiration date: an onion site that was "online" a month ago might be offline today. The system tracks the freshness of each enrichment and flags data that is potentially stale.
  • 3.Smart deduplication — The same victim can be reported by multiple sources with slightly different names. Fuzzy matching identifies duplicates and links them, keeping the original provenance of each record.
  • 4.Source health verification — External sources can degrade or disappear without notice. Automatic health monitoring periodically checks the reachability and integrity of each source, flagging anomalies before they affect data quality.

Enrichment pipeline

Each ransomware group is enriched through a multi-phase pipeline that combines data from independent sources:

PhaseSourceMatchingData added
1ransomware.liveDirect name (source of truth)Basic profile, victims, attacks, infrastructure, BTC addresses, lineage
2MITRE ATT&CKNormalized name + aliasesTTPs by tactic, software tools, references, additional aliases
3RansomwhereBTC address (primary) + name (secondary)BTC transactions with USD amounts, wallet addresses, dates
4deepdarkCTINormalized nameOnion site status, URLs, communication channels (Tox, Telegram, Twitter, email)

Matching strategy

Matching across different sources is the central problem of CTI aggregation. Elementary CTI uses a multi-level strategy:

  • →Direct matching — BTC address or unique ID shared between the source and the database. Highest confidence, zero ambiguity.
  • →Normalized name — Lowercase, spaces/hyphens/underscores removed. For example, "LockBit 3.0" → "lockbit30", "ALPHV" → "alphv". Covers most cases.
  • →Alias lookup — Comparison with the list of known aliases (MITRE merge + ransomware.live altname). For example, "BlackCat" found as an alias of "ALPHV".
  • →Skip list — Ambiguous or generic names (for example, "unknown", "test", "new") are excluded from matching to avoid false positives.

Known limitations

  • →Data reflects the last observation from each source, not the real-time state. An "online" onion site might already be offline.
  • →Name matching does not capture every case: groups with completely different names across sources require manual mapping.
  • →Ransomwhere covers only a fraction of ransomware families (29/136 matched out of ~360 total groups).
  • →deepdarkCTI is community-curated and can contain incomplete or outdated data for lesser-known groups.
  • →Absence of data is not evidence of absence: a group without MITRE TTPs might simply not have been documented yet.
